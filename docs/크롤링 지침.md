# 크롤링 지침

게임 공지/게시글 일 1회 폴링 agent 프로젝트의 차단 회피 및 안전 운영 지침.

---

## 1. 기본 원칙

일 1회 폴링이면 IP 차단 가능성은 거의 없다. 사람인 판례에서 차단 트리거가 된 건 *고빈도 + 우회까지* 했을 때이며, 아래 수칙만 지키면 안전 마진이 충분하다.

---

## 2. 차단 회피 기본 수칙 (게임사·디시·아카 공통)

### 2-1. 호스트당 호출 수 최소화
- 목록 1페이지 + 새 글 N개만 호출.
- 전체 페이지 순회 금지.

### 2-2. 요청 간 간격
- 같은 호스트 호출 사이 `2~5초 sleep` + jitter (±30%).
- 고정 간격보다 jitter를 주는 편이 봇 탐지에 덜 걸린다.
- 어댑터별로 `polite_sleep_min/max` 클래스 변수로 override. robots.txt `Crawl-Delay` 가 명시되면 그 값 이상으로 설정.
  - 현재 dcinside 만 30~35s, 나머지 4개 어댑터는 기본 2~5s.
- **호스트가 다른** 어댑터들을 `asyncio.gather` 로 병렬 실행하는 것은 매너 위반이 아님 (`scripts/collect_all.py` 참조). 같은 host 어댑터가 둘 이상이면 `adapters/runner.py` 의 host 단위 Semaphore 가 자동 직렬화.

### 2-3. 헤더 정상화
- `User-Agent`: 평범한 데스크톱 Chrome 1개 사용
  - **단, 디시인사이드는 예외** — `User-Agent: dcinside.app` 필수
- `Accept-Language: ko-KR,ko;q=0.9`
- `Referer`: 해당 사이트 자체 도메인
  - 디시는 `Referer: http://www.dcinside.com` 필수

### 2-4. 재시도 정책
- 403/429/5xx 받으면 **즉시 재시도 금지**.
- 지수 백오프 적용: `5s → 10s → 30s`.
- 3회 실패 시 그 사이트는 그날 스킵.

### 2-5. 세션 쿠키 유지
- `httpx.Client()` 한 인스턴스로 한 사이트 호출을 묶음.
- 브라우저처럼 보이게 하는 효과.

### 2-6. 로그 + 알림
- 막혔을 때 본인에게 알림이 가도록 설계.
- 조용히 빈 결과 반환은 위험 (장애 인지 불가).

---

## 3. 비용 0의 안전망

### 3-1. 로컬 캐시
- 한 번 받은 글은 SQLite/JSON에 저장.
- 같은 글 재요청 절대 안 함.

### 3-2. 장애 fallback 순서
1. `httpx`로 시도
2. 실패 시 **다음 폴링 주기에** `cloudscraper`로 재시도
3. 그래도 실패면 **다음 폴링 주기에** Playwright + stealth로 재시도

> **중요**: 실시간 자동 escalation은 오히려 *우회 시도로 보일 수 있어* 비추천.
> 같은 회차 안에서 도구를 바꾸지 말고, **다음 회차에 단계를 올리는** 게 안전하다.

### 3-3. Jina Reader 우회
- 게임사 공지처럼 가벼운 페이지는 `https://r.jina.ai/<URL>` 한 줄로 가져오면 본인 IP가 아예 사이트에 안 닿음 (Jina가 대신 fetch).
- Cloudflare 강한 사이트엔 약하지만 게임사 공지엔 깔끔.

---

## 4. 예외 케이스: 아카라이브 451

- 일부 성인/특정 채널은 **한국 IP 자체를 차단** (HTTP 451).
- 빈도 문제가 아니라 정책이라 어떤 헤더로도 안 풀린다.
- 해당 채널이 타겟이면 별도 대응 필요 (해외 프록시 등 — 단 사람인 판례상 영업적 차단 우회는 위험 가중 요소).

---

## 5. 요약

**2~5초 간격 + 1페이지만 + 지수 백오프** 세 가지로 일 1회 운영은 차단 발생 자체가 거의 0이다.

---

## 6. config 기반 엔진의 정책 적용

`engine/` + `scripts/register.py` + `scripts/poll.py` 의 자동 경로는 위 §2 를 따른다. 다만 다음은 명시적으로 결정된 사항:

- **요청 간 간격은 항상 엔진이 강제** — `ConfigAdapter` 공통 기본 3~6초 + ±30% jitter, 같은 host 는 `runner.collect_parallel` 의 Semaphore 로 자동 직렬화. 이건 "정책"이라기보다 *봇이 IP 밴 안 당하게 하는 안전장치*다.
- **사이트별 Crawl-Delay 는 config 의 `polite_sleep` 로** — Gemini 가 등록 시 robots.txt 의 `Crawl-Delay` 를 읽어 config 에 넣고(예: dcinside `{min:30,max:35}`), 엔진은 그 값을 *하한* 으로 쓴다(기본값보다 느릴 때만 적용). 엔진이 런타임마다 robots.txt 를 다시 읽어 사이트별로 클램핑하지는 않는다 — 그건 이번 스코프에서 뺐다.
- **robots.txt `Disallow`** — `register.py` 가 등록 시 한 번 체크해서, 해당 경로가 명시적으로 금지돼 있으면 **경고만 띄우고 진행**한다(자동 거부 아님). `Disallow: /` (사이트 전체 금지) 면 더 강한 경고.
- **`LOGIN_REQUIRED` 사이트는 자동 등록 거부 (rc=2 policy_reject)** — 로그인 자동화는 안 한다(사용자가 수동으로 한 번). 이건 *정책상* 미지원 — 능력 문제 아님.
- **anti-bot/captcha 차단 = `capability_blocked` (rc=5), 정책 거부 아님** — 2026-05-21 정책 변경. captcha 로 사이트를 *못 들어가는 건 능력 부족이지 정책 거부가 아님* (사용자 결정). 자동 경로(`register.py`)는 rc=5 + `.FAILED.json` (영구거부 X, learned_blacklist X, `batch --failed` 재집음) 박고, **hand-config 가 stealth/anti-detection 어댑터로 재도전 가능**:
  - **허용**: real-UA, `Accept-Language`/`Referer` 정상화, TLS fingerprint 정상화(`curl_cffi`/`cloudscraper`), `playwright-stealth`(navigator.webdriver 등 anti-detection), §3-2 의 *다음 회차* escalation 사다리.
  - **여전히 비추천(case-by-case, ToS/법적 리스크)**: 유료 CAPTCHA 솔빙 서비스(2captcha 등), 공격적 IP 로테이션/프록시 풀 — 사람인 판례상 *영업적 차단 우회* 가중 요소. 단일 사이트 가치 ≫ 리스크일 때만 사용자 승인 후.
  - **불변**: §2-1·§2-2 (호출 최소화·polite_sleep) 는 stealth 어댑터에도 그대로 — stealth = *덜 탐지되게* 지 *더 때리게* 가 아님.
- **요약본만 푸시, 원문 재배포 금지** — 엔진은 `content_html` 까지 저장하지만, 그걸 그대로 보내지 않는 건 다운스트림 요약·알림 컴포넌트의 책임이다.
- 깨짐(사이트 구조 변경) 감지 시 재-probe 는 *연속 2회* 깨졌을 때만 — 일시 장애에 떨지 않게, 그리고 재-probe 폭주를 막게.
