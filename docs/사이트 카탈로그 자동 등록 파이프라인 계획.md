# 사이트 카탈로그 자동 등록 파이프라인 계획 (2026-05-19)

## 1. 동기

사용자가 직접 사이트를 찾아 Discord/봇에 등록하기엔 후보 풀이 좁다. `docs/[연구] 게시판 형태 플랫폼 크롤링 분류 가이드 …` (사전 설계 문서) 가 글로벌·한국 게임/포럼/커뮤니티 60+ 사이트를 5-tier 난이도(arXiv 2601.06301) × 9개 플랫폼 카테고리로 정리해 둠. 그 자료를 직접 카탈로그화해서 일괄 `register.py` 돌리고, 결과 분포를 dashboard 에서 한눈에 본다.

## 2. 목표 / 비목표

**목표**
- 다른 사람이 조사한 사이트 목록을 **machine-readable 카탈로그** 로 변환.
- 그 카탈로그를 입력으로 받아 `scripts/register.py` 를 **idempotent 하게 일괄 실행** 하는 driver.
- dashboard 에 **카테고리 × tier × 결과** 분포 화면.
- 모든 phase 에 **codex 리뷰** 게이트.

**비목표**
- 등록 자체의 자동화 품질 향상 (`register.py` 자체 개선은 hand-config 워크플로우 영역).
- Cloudflare/CAPTCHA 우회 (정책 — 차단되면 거부로 카운트).
- N100 봇에서 batch 자동 실행 (dev box 수동 실행 only — CLAUDE.md §2 룰 B).

## 3. 데이터 모델 — 후보 카탈로그

위치: `configs/candidates/catalog.yaml`. 단일 파일 (~70 entry). git 추적.

스키마 (entry 1개):

```yaml
- id: nexon-mabinogi-notice       # 안정 ID (안 바뀜, dashboard URL 에 박힘).
  name: 마비노기 공지
  category: kr-game-official      # enum (§3a)
  tier: A                          # enum A~G (§3b)
  expected_strategy: httpx_html    # enum: rss / httpx_json / httpx_html / playwright_html / handwritten / unknown
  boards:                          # 1 entry 안에서 여러 게시판. 각 board = 독립 slug = 독립 register 호출.
    - url: https://mabinogi.nexon.com/page/news/notice_list.asp
      label: 공지
    - url: https://mabinogi.nexon.com/page/news/update_list.asp
      label: 업데이트
  note: 정적 ASP. 자동등록 잘 됨 예상.
  source:
    doc: "docs/[연구] … 사전 설계 문서.md"
    section: "5) 한국 게임"
    provenance: doc                # doc | history | web. dashboard 에 표시.
```

**codex review #1 반영**: `urls: [...]` (의미 모호 — alternates? sub-boards?) 를 `boards: [{url, label}]` 로 변경. 각 board 가 register.py 1회 호출 = 1 slug. 같은 entry 의 여러 board 는 dashboard 에서 "같은 사이트의 sub-board" 로 묶임.

### 3a. `category` enum
```
global-game-store       Steam, Epic, GOG
global-game-official    Riot, Blizzard, Nintendo, HoYoverse
kr-game-official        Nexon, NCsoft, Smilegate, Krafton, Pearl Abyss
global-community        Reddit, Discord, Twitter/X
forum-engine            Discourse, vBulletin, XenForo, phpBB
kr-community-open       Ruliweb, Clien, Inven
kr-community-blocked    Arca, DCInside
kr-community-login      Naver Cafe
social-media            Twitter, Instagram, TikTok (대부분 skip)
news-wiki               일반 뉴스, Wikipedia
```

### 3b. `tier` enum (arXiv 2601.06301 5-tier 매핑)
```
A  정적 HTML            Simple HTML
B  서버 렌더 + hydration  Complex HTML
C  SPA + JSON XHR        Complex HTML
D  SPA + auth/CSRF       Simple Auth / Complex Auth
E  Heavy SPA + bot 보호  CAPTCHA (Cloudflare 등)
F  iframe-in-iframe      —
G  CAPTCHA-gated         CAPTCHA
```

### 3c. `expected_strategy`
도큐멘트의 "권장 접근법" 컬럼 그대로. `register.py` 가 실제로 만든 strategy 가 이 값과 다르면 dashboard 에서 ⚠ 표시(휴리스틱 정확도 모니터).

## 4. 카탈로그 source

세 source 합집합 (사용자 선택대로):

1. **사전 설계 문서** (1차, provenance=`doc`) — section 1 (기술 구조 분류), section 2 (플랫폼 종류), section 5 (게임 매트릭스). 표에 적힌 구체 URL + 한국 게임사 공식 URL 들. ~40 entry.
2. **`docs/사이트별 등록 시도 기록.md`** (provenance=`history`) — 10 entry. 이미 등록 시도된 사이트 → 카탈로그에 박되 `note` 에 "이미 등록됨/손작성/손어댑터" 표기 (idempotency 가 skip 처리).
3. **Web 추가 조사** (provenance=`web`) — WebSearch 로 한국 게임 공지 URL 보강. **명시 워크플로 (codex review #1)**: 
   - 검색 쿼리: 한국 주요 미디어/장르별 게임 — "게임명 공지사항 게시판" / "official patch notes". 
   - 결과 URL 마다 도메인이 doc 의 9 카테고리에 들어가야 카탈로그 admit. 못 들어가면 reject.
   - 보수적으로 ~10 entry 까지. provenance=`web` 으로 박혀 dashboard 가 출처 구분.

dedup: 같은 host+path 면 1개 entry (boards 배열에 여러 게시판 URL — §3 스키마).

## 5. Batch driver — `scripts/register_batch.py`

CLI:
```
python scripts/register_batch.py [--category=...] [--tier=A,B] [--limit=N] [--dry-run] [--cooldown-days=7] [--pull-snapshot]
```

흐름 per URL:
1. `slug = url_to_slug(url)` (probe.paths)
2. **N100 snapshot 동기화** (선택, 전체 run 시작 시 1회) — `--pull-snapshot` 가 켜져 있으면 `scripts/triage.py pull --skip-later` 로 N100 의 `configs/` + `output/poll_state/` 를 dev box `configs.snapshot/` + `output/snapshot/poll_state/` 로 pull. **기본 OFF** (codex review #3 권고): network/scp 비용 큼, dry-run 엔 필요 없음. 대신 idempotency 체크가 dev box `configs/` + 기존 snapshot 양쪽을 항상 봄. **이유 (codex review #1)**: CLAUDE.md §5 rule C — N100 봇 `/watch` 가 dev box 보다 앞서 등록할 수 있어 같은 URL 을 다시 register 하면 비용 낭비 + 충돌. snapshot stale 우려 시 사용자가 명시적으로 켜기.
3. **skip 판단** (idempotent):
   - `configs/<slug>.json` (dev box) **또는 snapshot 의 같은 slug** 존재 → status=`already_registered`, skip
   - `output/poll_state/<slug>.REJECTED.json` 존재 → status=`already_rejected`, skip
   - `output/poll_state/<slug>.FAILED.json` 있고 cooldown 내 → status=`recent_fail_skip`, skip
   - `output/triage_later.json` 의 later set 에 포함 → status=`triage_later`, skip
4. **실행**: `subprocess.run([python, scripts/register.py, url, --max-attempts, N], timeout=900, capture_output=True)` (15분 / URL).
   - **stderr 도 캡처** — rc=2 가 policy_rejected 인지 argparse error 인지 구분하기 위함 (둘 다 exit code 2). argparse 실패면 stderr 첫 줄에 "usage: register.py" 가 박힘.
5. **결과 분류** (codex review #1 반영 — 모든 rc 명시 매핑):
   - rc=0 + `configs/<slug>.json` 존재 → `registered`
   - rc=0 + config 부재 → `error_no_config` (이론상 없음 — 안전망)
   - rc=1 → `failed` (generation 실패 — `.FAILED.json` 보통 동반)
   - rc=2 + stderr 에 `usage:` 시작 → `error_cli` (driver 버그)
   - rc=2 + 그 외 → `policy_rejected` (BLOCKED/LOGIN)
   - rc=3 → `gate_rejected` (recognize_reject / single-article nav-only / meta-diverging / multi_host_hub / root_marketing)
   - rc=4 → `error_cli` (`--unlearn`/`--clear-bug` invalid — 안 씀, 안전망)
   - rc=6 / rc=7 → `error_unexpected` (`--gate-only` 전용 — batch 가 안 쓰는 플래그라 발생하면 driver bug)
   - timeout / 그 외 → `error_runtime`
6. **strategy 추출**: `configs/<slug>.json` 의 `strategy` 필드 + `adapter` 필드 (있으면). 즉 *실제로 작성된 config* 기준 (codex review #1: recognizer fast-path 가 probe 없이 config 생성하므로 probe digest 의 strategy 가 아니라 written config 의 strategy 가 정답).
7. **outcome 기록**: `output/register_batch_runs.sqlite3` (dev box only — git ignored, snapshot 대상 X). table `runs(ts, cand_id, url, slug, category, tier, expected_strategy, actual_strategy, actual_adapter, rc, status, reason, duration_s, stderr_tail)`.
   - sqlite 선택 이유: dashboard 가 cases.sqlite3 와 동일 패턴으로 read-only 쿼리. jsonl 은 통계 매번 풀스캔.
   - 같은 (cand_id, url) 여러 번 시도하면 row 가 누적 (최신 ts 만 보이게 dashboard 가 group by).

`--dry-run`: skip 판단까지만, register 안 돌림 (현재 상태 분포만 확인).

`--limit=N`: 가장 안 시도된 entry N 개만 (last_attempted_at NULL → 오래된 순). 한 번에 60건 다 못 돌리니 chunk 단위.

`--concurrency`: **항상 1**. 이유 (codex review #1): Gemini key 단일 + `engine/recognizers/learned_blacklist.json` 의 write lock 이 Windows 에선 사실상 no-op → 병렬 시 corruption 위험. politeness 는 부수적.

## 6. Dashboard `/candidates`

좌측 nav 에 `🌐 Candidates` 추가.

페이지 구성:
1. **요약 KPI 박스** — 총 후보 N, 등록됨 N (%), 거부됨 N (%), 실패 N (%), 미시도 N (%).
2. **카테고리 × tier matrix** — 행=category, 열=tier(A~G), 셀=`{registered}/{total}` + 색상(green/yellow/red).
3. **결과별 stacked bar** — 카테고리별로 registered/rejected/failed/untried 비율.
4. **상세 표** — 각 entry 한 행: `id`, name, category, tier, expected_strategy, actual_strategy, status, last_attempted_at, slug(→`/subs/<slug>` 링크 if registered, →`/triage/failed#<slug>` if failed).
5. **필터** — category, tier, status, q(name/url 검색).

데이터 source: `register_batch_runs` 테이블 LEFT JOIN catalog yaml (in-memory load). configs/poll_state/ 파일 (snapshot) 도 확인해서 batch 밖에서 등록된 것도 잡음 (e.g. 봇 `/watch` 로 등록된 사이트와 카탈로그 url 매칭).

**preflight middleware 영향 (codex review #1)**: `dashboard/app.py:74` 의 `_preflight_pull` 이 `/candidates` GET 시에도 N100 snapshot pull 시도. `register_batch_runs.sqlite3` 자체는 dev box 전용이지만, snapshot 의 `configs/` 와 매칭하는 부분은 snapshot 이 있어야 정확. middleware 가 실패해도 stale snapshot 으로 fallback 하므로 `/candidates` 는 그래도 sqlite 만 보고 렌더 가능 — 단지 "batch 밖 등록" 매칭이 stale 일 수 있음. 별도 skip 안 함.

Chart.js / Plotly **안 씀** — Pico CSS + 인라인 SVG 또는 progress bar 로 충분. 의존성 추가 회피.

## 7. Codex review 게이트

사용자가 원래 5게이트 요청했지만 codex review #1 가 "3 게이트로 충분" 권고. 사용자 선택대로 5 게이트 유지하되 #1/#5 는 짧게:

| 게이트 | 시점 | 입력 | 출력 |
|---|---|---|---|
| #1 | 이 문서 작성 직후 ✅ 완료 | 이 plan doc + register.py rc/state file 정황 | BLOCKERS 3건 + SHOULD-FIX 6건 → 이 doc rev2 에 반영 |
| #2 | Phase A yaml 작성 후 | `catalog.yaml` + 이 plan | schema 위반 / dedup 누락 / tier 오분류 / provenance 누락 |
| #3 | Phase B `register_batch.py` 작성 후 | 새 파일 + plan §5 | idempotency 결함 / rc 매핑 누락 / sqlite race / argparse-error 오인 |
| #4 | Phase C dashboard view 작성 후 | 새 router + template + plan §6 | XSS / safe_slug 미적용 / N+1 query |
| #5 | 모든 phase 끝 | 전체 diff | 통합 결함 / 누수 |

호출 방식: `Agent(subagent_type='codex:codex-rescue', model='sonnet', prompt=...)`. plan-only 리뷰는 자료 다 본 read-only.

## 9. 위험 / 미해결

- **rc 코드 누락**: register.py 가 rc=1 case (generation 실패) 등 명시 안 됨 → §5 step 4 의 "그 외 + FAILED" fallthrough 로 잡음. codex review #3 에서 확인.
- **카탈로그 drift**: 사이트 URL 바뀌면 yaml stale. dashboard 의 actual vs expected 비교가 detection 신호 — 별도 알람은 안 짜.
- **N100 sync**: batch driver 가 dev box 에서 만든 configs/ 는 commit 후 push → N100 pull 이라야 봇에 반영됨. 일반 배포 사이클 (CLAUDE.md §2) 그대로.
- **Gemini 비용**: 60 entry × ~$0.01 ≈ $0.60. 카테고리별/tier 별 segment 실행으로 조절.
