## 0. 배경

### 0a. 무엇이 문제인가
자동 등록 파이프라인(probe → digest → Gemini → config JSON → engine)이 실패한 사이트는 사람 + Claude Code 가 손-config 한다. 이 과정에서 Claude 는 *자율적으로* probe/prompt/schema/코드를 손댈 수 있는데:

1. **버그 위험** — 자율 변경이 21개 기존 사이트 회귀 일으킬 수 있음.
2. **누더기 위험** — 같은 종류 실패에 매번 다른 자리에 박으면 시스템 일관성 깨짐.
3. **prompt rot** — `prompts/config_writer.system.txt` 의 룰이 시간 따라 죽거나 중복.
4. **단일 doc 의존** — `docs/사이트별 등록 시도 기록.md` 한 파일에 모든 케이스 → grep 어려움 + 병합 충돌 + rot 검출 안 됨.

### 0b. 이전 plan(audit-1·2·3) 의 교훈
원안(plan v1 — 4주 인프라: tests/sites stage 4 + llm_eval + INDEX.json + cap + self-verification)·v2(reviewer 추가 + R-XYZ + per-case) 둘 다 audit 가 깬 한계:
- **tests/sites stage 4** = raw HTML 캡처 메커니즘 침묵 (validate.py 가 raw 폐기) + adapter 의 절반 fetch/parse 분리 안 됨 → 작동 X
- **llm_eval** = 비결정 + model deprecate 감지 미정의 + cost cap silent break → 신뢰 0
- **INDEX.json** vs 기존 md = 중복 rot 면적 2배
- **layer rubric 강제** = reviewer subagent 의 Bash 미검증 + self-modification 미tigated → theater
- **R-XYZ + grep rot detection** = `prompt_sections_relevant` 필드 optional → 빈 필드 천지 → false-positive rot 천지 → DOA
- **§7 trigger thresholds (30+/5+)** = 도달까지 2-5개월 → 인프라 ROI 부족
- **"무인" 약속** = branch protection·model rotation·--no-verify 가드 다 user/behavior 의존

### 0c. v3 의 핵심 통찰

**prompt 변경의 *두 종류* 를 분리**:

| 종류 | 누가 | 데이터 흐름 |
|---|---|---|
| **prompt 추가 (additive)** — 새 패턴 → 새 룰 한 줄 | hand-config 에서 자율 (필요 시) | 그 시점 *케이스 기록* 으로 충분 |
| **prompt 개선 (curative)** — 죽은 룰 제거 / 중복 머지 / 모순 정리 | 별도 SKILL `prompt-rot-review` (장래) | 누적 cases 분석 필요 |

이 분리로:
- hand-config = *지금 만들 데이터* 만 만들면 됨 (case 파일)
- prompt-rot-review SKILL = *누적 데이터를 능동적으로 분석* — 빈 필드 있어도 SKILL 이 추론
- audit-3 #1 (R-XYZ rot detection DOA) 자연 해소 — 그 메커니즘 hand-config 책임 아님

### 0d. 다섯 자리 (fix-knowledge layers) — 재확인

| 자리 | 압력 시점 | 비용 |
|---|---|---|
| **(E) schema 거부** | config 생성 직후 | 낮음, hard |
| **(D) retry feedback** | 1~4차 사이 | 낮음 |
| **(C) probe digest 신호** | probe 단계 | 높음 (휴리스틱 + fixture + contract) |
| **(B) few-shot** | 매 prompt | 토큰 비쌈 |
| **(A) system 규칙 *추가*** | 매 prompt | 추가만 OK, 수정/제거 X (별도 SKILL) |
| **(F) 새 엔진 코드** | 코드 자체 | 큼, sub-카테고리 4종 |

원칙: 싸고 hard 한 쪽부터. (A) 추가 가능, (A) 수정/제거 는 hand-config 영역 아님.

## 1. 핵심 설계

### 1a. hand-config 사이클 (매 케이스)

```
1. /report 또는 /preview 실패 → Claude 모드 B 시작
2. 진단 + 픽스 시도 (E/D/C/B/A/F 자율, A 는 *추가* 만)
3. SKILL.md 5-질문 자가 점검 — 가이드라인, 권장
   ① 어느 자리? ② 이전 케이스? ③ 누구 깰까? ④ 검증 그린? ⑤ 결정 메모
4. docs/cases/<slug>.md 작성 (frontmatter 일부 필수)
5. python scripts/cases_index.py — INDEX.md 갱신
6. main thread 가 python scripts/probe_smoke.py 실행 — 결과 캡처
7. Agent(subagent_type='hand-config-reviewer', model='sonnet') 호출
   - main thread 가 diff + case 파일 + smoke 결과 prompt 에 박음
   - reviewer 는 *판단만* (Bash 없어도 작동)
   - PASS / FAIL 보고
8. FAIL → user 에게 보고. user 가 결정 (자동 재호출 X)
9. PASS → git commit + push
10. pre-push hook = probe_smoke 한 번 더 (안전망)
11. N100 ssh 배포
```

### 1b. 별도 SKILL `prompt-rot-review` (장래, *지금 안 만듦*)

```
사용자가 명시 호출 (예: "prompt rot 점검")
→ SKILL 이 prompts/ 전체 + docs/cases/*.md 전수조사
→ 죽은 룰 / 중복 / 모순 / 과spec 진단 보고
→ 사용자 승인 후 prompt 수정
```

트리거 조건: case 50+ 누적 또는 prompt 200줄+ 또는 사용자 직감.
