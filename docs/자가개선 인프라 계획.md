## 0. 배경 — 왜 이 인프라가 필요한가

자동 등록 파이프라인(probe → digest → Gemini → config JSON → engine)이 실패한 사이트는 사람+Claude Code 가 손-config 한다. 이 과정에서 **probe 휴리스틱·prompt·schema** 를 *개선* 할 수 있는데, 현재는:

1. 회귀 검출 부재 — probe 한 줄 바꾸면 다음 사이트 등록 산출 config 가 달라짐. 이미 등록된 21개는 안전(`configs/*.json` 이 디스크에 immutable)하지만 *등록 경로* 는 무방비.
2. 프롬프트 변경 효과 측정 부재 — Gemini 출력 비결정. "이 한 줄 추가가 통과율 올렸나" 알 수 없음.
3. 메모리 부재 — `docs/사이트별 등록 시도 기록.md` 가 사람용. Claude/LLM 이 트레이닝 자료로 못 씀.
4. layer-choice 휘둘림 — 같은 실패에 (E) schema 픽스 / (D) retry feedback / (C) probe 휴리스틱 / (B) few-shot / (A) system 규칙 5자리. Claude 가 매번 그때그때 판단 → 누더기 위험.

## 0a. 다섯 자리 (fix-knowledge layers) — 재확인

| 자리 | 압력 시점 | 비용 | 보장 |
|---|---|---|---|
| **(E) schema 거부** | config 생성 직후, fetch_list 전 | 낮음(validate 한 줄) | **hard** — LLM 무시 못 함 |
| **(D) retry feedback** | 1차 실패 → 2~4차 사이 | 낮음(feedback 텍스트 + 검증기) | LLM 의존, 4회 안 |
| **(C) probe digest 신호** | probe 단계, config 생성 *전* | 높음 (휴리스틱 + unit fixture + contract + smoke) | LLM 의존, first-try |
| **(B) few-shot** | 매 prompt | 토큰 비쌈 (~수천/예제) | LLM 모방, 강함 |
| **(A) system 규칙** | 매 prompt | 토큰 + 잡음 누적 | LLM 의존, 추상 |
| **(F) 새 엔진 코드 경로** (audit 추가) | 코드 자체 | 큼(설계+구현) | E-A 어디에도 안 맞을 때만 |

원칙: **싸고 hard 한 쪽부터 (E > D > C > B > A > F)**. 데이터/검증 측에 박는 게 system.txt 한 줄보다 거의 항상 우수.

## 3. Phase 별 구체 task

### P1 — parse/fetch 분리 리팩터

목표: 모든 strategy/adapter 에 *순수 parse 함수* 추가 — frozen HTML/JSON 으로부터 posts 추출. 네트워크 0 호출.

#### P1-a. `engine/strategies/httpx_json.py`
- 현재 `fetch_list` 안에 `_get_json` → list_path/item_path 추출 인라인. 51-94 라인.
- 분리 — `parse_list_json(adapter, payload, *, page=1, page_size=...) -> list[NoticePost]` 신규.
- `fetch_list` 는 `_get_json` 후 새 `parse_list_json` 호출만.
- `fetch_article` 도 `parse_article_json(payload)` 분리 (필요 시).
- 검증: `python scripts/probe_smoke.py --stage 3` 그린 + 손-실행 (`endfield_official` config 으로 `fetch_list` 결과 N건 비교).

#### P1-b. `engine/strategies/playwright_html.py`
- `parse_list_html` 은 이미 `httpx_html` 의 것 재사용 (`playwright_html.py:20`). 그러므로 `_goto + page.content()` 결과를 HTML 문자열로 받아 같은 함수에 통과시키도록 구조만 명확화.
- fixture 주입 경로 추가: env var `NW_FIXTURE_HTML_PATH` 가 있으면 browser launch 생략하고 그 HTML 을 사용 — 테스트 전용. 또는 `parse_list_html_from_string` 같은 명시 API 제공.

#### P1-c. adapters 7개
- 각 adapter (`NaverCafeAdapter`, `DaumCafeAdapter`, `ArcaLiveAdapter`, `DCInsideMGalleryAdapter`, `SkkuCseAdapter`, `EndfieldAdapter`, `RedditAdapter`) 의 `fetch_list` 에서 네트워크 호출(API call / browser navigate)과 파싱 로직 분리:
  - 네트워크 부분 → `_fetch_raw(page) -> bytes | str | dict` (그대로 유지)
  - 파싱 부분 → `parse_raw(self, raw, *, page=1) -> list[NoticePost]` (신규, 인스턴스 메서드)
  - `fetch_list` = `_fetch_raw` + `parse_raw`.
- 각 adapter PR 별도 (병렬 가능).

#### P1-d. 검증 (모든 P1 PR 끝)
- `scripts/probe_smoke.py --stage 3` 그린.
- `scripts/inspect_subs.py` 또는 손-실행: 21 configs 전수 `fetch_list(page=1)` 결과 baseline 과 동일한지 (post_id 셋 동일 여부).

## 4. 회피해야 할 함정 (audit 가 짚은 것)

### F1. Stage 4 가 반쪽 됨
- P1 다 끝나기 전엔 stage 4 활성화 X. P1-a/b/c 다 그린 + 21 configs 회귀 확인 후 stage 4 enable.
- 부분 활성화 시 *비대칭 커버리지* 가 신뢰 환상 만듦. 차라리 끄는 게 정직.

### F2. expected.json 의 토톨로지
- `post0_title_regex` 는 *결정성* 만 검증, *진실* 안 검증. 사이트 드리프트는 stage 4 못 잡음.
- 진실 검증은 별도 — N100 폴링 자체 + `/report` 가 이미 역할 함. stage 4 는 *엔진 변경의 회귀* 한정 가드.

### F3. INDEX.json 의 거짓 메모리
- `docs/사이트별 등록 시도 기록.md` 와 *중복* 되지 않게 — INDEX.json 은 *Claude 가 읽는 구조화 메모리*, doc 은 *사람 읽는 서술*. 같은 case 가 양쪽에 있어야 함 — 한쪽만 갱신하면 rot.
- 모드 B step 5c (`code-audit-reviewer`) 가 "INDEX 와 doc 둘 다 갱신했나" 체크 항목 포함.
- 증상-키 lookup 위험 (Mabinogi/Nexon-forum 둘 다 `[FAIL] posts_nonempty` 인데 root cause 다름) — INDEX 검색 시 *root_cause* 일치 봐야지 *pattern* 만 보면 안 됨.

### F4. cap·rubric 무강제
- cap (system.txt ≤ 150) 은 stage 1d 가 강제 — 자가-순찰 아님.
- rubric 위반은 P7 의 code-audit-reviewer 가 차단. 사용자가 명시 승인하면 우회 가능 (`# RUBRIC-WAIVER: <이유>` 주석 + 사용자 PR comment).

### F5. 인지 부하 폭증
- 케이스당 touch ~17개 파일. 자동화 가능한 부분 도구화:
  - auto-snapshot 훅 (P4) — fixture 자동.
  - INDEX 엔트리는 `triage.py` 가 `last_failure_pattern` 추측해 prefill — 사용자가 확정.
  - `docs/사이트별 등록 시도 기록.md` 갱신은 P7 reviewer 가 누락 검출만.
- 그래도 부담 큼 — 케이스당 1시간 예상. dev-stage 이후엔 사이트당 ROI 다시 평가.

### F6. Ratchet 의 slow-bleed
- "fixture 가 stage 4 fail → fixture 를 새로 찍어 통과" 회피 메커니즘 필요.
- `tests/sites/<slug>/expected.json` 변경 PR 은 별도 — *fixture 갱신 PR 은 commit 메시지 에 `[fixture-refresh: <reason>]` prefix + 새 expected 값과 옛 값 모두 PR 본문에 명시* 강제 (P7 reviewer 검출).
- fixture-refresh 빈도 모니터링 — 같은 slug 의 fixture 가 3개월 안 2회 갱신되면 그건 engine 회귀 신호 (alert).

### F7. 재귀적 자율성 (제안 자체를 Claude 가 수정)
- 보호:
  - `scripts/probe_smoke.py` 의 stage 1d 가 *system.txt cap* + *rule ID 형식* 강제. 변경하려면 stage 1d 코드 자체를 고쳐야 함 — diff 가 명확히 보임.
  - `SKILL.md` 변경은 항상 PR review (사용자가 GitHub 측 branch protection 으로 직접 강제).
  - 이 plan 문서 (`docs/자가개선 인프라 계획.md`) 변경은 별도 PR + 사용자 명시 승인.
