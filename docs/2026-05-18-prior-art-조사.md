# 2026-05-18 — prior-art 조사: URL → 글 추출 도구 비교

중간발표(2026-05-18) 후 자기점검. 기존에 시장/학술에 존재하는 "URL → 글 추출" 도구를 *조사도 안 하고* 코딩 에이전트로 처음부터 구현한 것이 잘못이었나? 결론을 추측이 아니라 **실증 bench** 로 내자.

실험 코드·결과 = [`experiments/prior-art-bench/`](../experiments/prior-art-bench/) (별 작업 폴더, README·plan·matrix·notes 포함).

본 문서 = 조사로 *새로 알게 된 점* + *우리 거에 빌릴 수 있는 패턴* 정리.

## 1. 시장 도구 mapping (이전엔 모름)

| 도구 | 종류 | 한 줄 |
|---|---|---|
| [Crawl4AI](https://github.com/unclecode/crawl4ai) | OSS Python, playwright | `JsonCssExtractionStrategy` (사람 selector) + `LLMExtractionStrategy` (자동, LiteLLM 통해 Gemini 가능) |
| [llm-scraper](https://github.com/mishushakov/llm-scraper) | OSS TypeScript, playwright | Zod schema + Vercel AI SDK. `format: html/markdown/text/image` 5종. `generate()` = 재사용 playwright script 산출 |
| [Firecrawl](https://firecrawl.dev) | hosted (free 500 credit + 1000/월) | scrape / crawl / **map** / extract / search endpoint. JSON mode = schema + LLM 자동 |
| [ScrapeGraphAI](https://scrapegraphai.com/) | OSS Python | graph 기반 LLM scraping (bench 대상 X) |
| [FetchRSS](https://fetchrss.com/) | hosted | 임의 URL → RSS 변환 + 폴링. API 는 selector 손-박기 강제 (자동성 비교 의미 X) |

추가:
- [AutoScraper 논문 (arxiv 2404.12753, 2024)](https://arxiv.org/html/2404.12753v2) — "A Progressive Understanding Web Agent for Web Scraper Generation". 우리 register 단계의 학술 버전. **읽고 비교** 가치.
- [arxiv 2601.06301 (2026)](https://arxiv.org/html/2601.06301v1) — "Beyond BeautifulSoup: Benchmarking LLM-Powered Web Scraping for Everyday Users". 35 사이트 × {BS4 / Scrapy / Claude / Simular.ai} bench. **우리 bench 의 western validity 확장 source**.
- [Wrapper induction 학술 분야](https://dl.acm.org/doi/10.5555/1218702.1218707) (2006~) — supervised (labeled example 학습) / unsupervised (구조 분석). 우리 `list_candidates.json` = wrapper induction 의 *candidate rule* 에 해당. 어휘 빌릴 가치.

## 2. 실증 bench 결과 (한국 사이트 5 × 도구 5 = 25 셀)

전체 매트릭스 → [`experiments/prior-art-bench/matrix.md`](../experiments/prior-art-bench/matrix.md)

| 사이트 (tier) | manual_bs4 | crawl4ai_css | crawl4ai_llm | llm_scraper | firecrawl_json |
|---|---|---|---|---|---|
| skku_cse (정적 JSP) | **R=1.00 / 0.4s / $0** | 1.00 / 5.6s | 1.00 / 17s | 1.00 / 16s | 1.00 / 55s |
| gamemeca (정적) | **1.00 / 1.4s** | 1.00 / 1.9s | 1.00 / 19s | 1.00 / 25s | 1.00 / 17s |
| nexon_bluearchive (SPA) | 0.00 | 0.00 | 0.00 | **1.00 / 20s** ⭐ | 0.70 / 22s |
| naver_cafe (iframe) | 1.00 / 0.9s | 0.00 | 1.00 / 11s | 1.00 / 11s | **1.00 / 23s** |
| arca_trickcal (CF) | 0.00 | 0.00 | 0.20 / 132s | **0.70 / 53s** ⭐ | 0.00 (Notice rows 만 ⚠️) |

- R = list_recall (top 10 GT 매칭 비율)
- LLM 셀 3회 변동 (variance) 측정: σ=0.00 (Gemini 결정적). 단 free tier rate limit 으로 일부 셀 throttled
- `manual_bs4` = `requests + BeautifulSoup + 사람-tuned selector`. 우리 `engine/strategies/httpx_html.py` runtime 과 *본질적으로 같음* — control baseline
- Firecrawl arca = 페이지 접근은 성공, 다만 *Notice (pinned 2024~2025) rows* 추출. prompt "recent posts" 의도 안 맞춤. prompt 조정 시 회복 가능성

### 5 결론

1. **정적 사이트 (3/5)** — `manual_bs4` 압승. LLM 도구 14~140배 느림, 정확도 동등. 자동 변환 불필요
2. **SPA (nexon)** — `llm_scraper` 만 1.00. 이유 = playwright `wait_until: 'networkidle'` 로 thread API 응답 대기. crawl4ai default 5s sleep 부족
3. **CF (arca)** — `llm_scraper` 0.70, `crawl4ai_llm` 0.20. **stealth 안 써도 일부 통과** (UA + webdriver-hide 정도)
4. **iframe (naver_cafe)** — cafe 홈 widget 으로 충분. iframe 진입 불필요
5. **우리 거 contribution 보존** — 어떤 도구도 polling, dedup, Discord, hand-config triage, fail_taxonomy 안 함. 단 **register (config writer) 단계 의 일부 사이트** 는 `llm_scraper` 로 *대체 가능*

## 3. 우리 거에 빌리거나 참고할 패턴

### 3a. ★★★ Firecrawl `/map` endpoint (즉시 통합 후보)

**기능**: URL 1개 던지면 *그 사이트의 internal link + sitemap.xml entry* list 반환.

bench live 테스트 결과:
- `https://cse.skku.edu/` → 15개 entry. `/cse/notice.do` 포함 ✅
- `https://www.gamemeca.com` → 11개. `/news.php` 포함 ✅
- `https://cafe.naver.com/gutterlife` → 1개 (홈만). iframe/login-walled → 한계 ❌

**활용**: 사용자가 도메인 또는 부정확한 URL 던질 때 (현재 FAILED 큐의 *"posts_nonempty=0"* 케이스 일부) → `/map` → 후보 list → config_writer prompt 에 "이 중 board page 골라" 추가 → 선택된 URL 로 probe 재시도.

**위치**: `bot/url_gate.py` 또는 신규 `engine/url_discovery.py`. 비용 = 1 credit / req.

**한계**: iframe-heavy / login-walled / SPA-only 사이트 (naver cafe, dcinside 일부 등) → 도움 안 됨. 이런 사이트는 *recognizer* 가 답.

### 3b. ★★ llm-scraper `generate()` (register 단계 비교)

**기능**: 페이지 + schema 던지면 *재사용 가능 playwright script* 생성. 한 번 만들면 LLM 없이 재실행.

```ts
const { code } = await scraper.generate(page, Output.object({ schema }));
const result = await page.evaluate(code);
```

**활용**: 우리 `generate/` 단계 의 *결과물* (JSON config) 와 *직접 비교 대상*. 어느 쪽이 폴링 시 효율적이고 정확한가:
- 우리 config JSON: engine 의 transform / pagination / fields 어휘로 표현 → 폴링 시 LLM 없음, vocab 안에 있어야 함
- llm-scraper script: 임의 playwright 코드 → vocab 제약 없음 (자유도 높음), 매 폴링 시 playwright 실행 비용

**비교 bench 작업 (별 작업)**: 같은 사이트에서 두 결과물의 selector 안정성·breakage 빈도·실행 cost 측정.

### 3c. ★ Crawl4AI `extraction_strategy` 추상화 패턴 (architecture inspiration)

**패턴**: `JsonCss` / `Cosine` / `LLM` 추출 strategy 가 *같은 인터페이스* (`extract(input) → items`) 구현. crawler 본체는 strategy 교체 가능.

**우리 거 현재**: `generate/` 단계 = Gemini 1가지. 미래 (다른 모델 / RAG / heuristic-only 1차) 추가 시 pluggable 화 고려할 가치. 지금은 over-engineering.

### 3d. (negative finding) markdown 변환 — 빌리지 마

**오해**: "markdown 변환 = token 절감"
**사실**: register 단계 = **selector 찾기** 가 목적. markdown 으로 변환 시 `class=`, `id=`, DOM hierarchy 손실 → selector 못 씀. config_writer 에 raw HTML 필수.

markdown 이 유효한 곳 = *runtime content fetch* (글 본문만 LLM 으로 정제) — 현재 selector 기반으로 잘 작동 중. 우선순위 낮음.

### 3e. (negative finding) networkidle wait — 이미 *더 똑똑*

**오해**: "llm-scraper 의 `wait_until: 'networkidle'` 빌릴 가치"
**사실**: 우리 `_wait_xhr_quiet` ([`engine/strategies/playwright_html.py:26`](../engine/strategies/playwright_html.py), [`probe/fetch_headless.py:87`](../probe/fetch_headless.py)) 가 vanilla networkidle 보다 우월:
- XHR/fetch/document 응답만 카운트 (광고 image/script 무시)
- quiet 500ms + hard cap 2000ms
- networkidle 이 광고 keepalive 로 영영 안 끝나는 사이트 (Google search, 뉴스 포털) 해결됨

bench 의 `crawl4ai` 셀 실패 = crawl4ai default 5s sleep 으로 진 것. 우리 코드와 무관.

단 — *2000ms hard cap* 이 nexon-class SPA-light 사이트의 thread API 응답 시간보다 짧을 수 있음. **별 점검 가치** (지금 prod 는 nexon 을 httpx_json 으로 우회해서 영향 없음).

### 3f. (잠재적) arca CF 통과 — stealth 강도 점검

**bench 발견**: arca.live 가 naive playwright + 3개 안티-fingerprint 옵션 (`--disable-blink-features=AutomationControlled` + `navigator.webdriver=undefined` + 정상 UA) 으로 *70% 통과*. 우리 prod 의 `ArcaLiveAdapter` 는 `playwright-stealth` 풀 패키지 사용 — *과한 방어* 가능성.

**확인할 점**: stealth 강도 낮춰도 안정성 유지되나? Cloudflare 변동성 큰 시간대 (한국 새벽 = CF 미국 오후) 변동 측정 필요. 별 작업.

## 4. 이전에 잘못 알았던 것 정정

| 기존 인식 | 정정 |
|---|---|
| "기존 도구 안 봐서 reinvent the wheel" | 부분만 맞음. runtime extraction 은 reinvent, **register + triage + polling 번들 = 시장에 없음** |
| "markdown 변환이 token 절감 win" | selector 손실 → config writer 손해. runtime content fetch 에만 유효 |
| "networkidle wait 빌릴 가치" | 우리 `_wait_xhr_quiet` 가 더 똑똑 |
| "arca CF = stealth 필수" | naive playwright + 3옵션 으로 70% 통과 가능 |
| "naver_cafe = 어차피 손-어댑터 destination" | 손-어댑터 = *영구 X*. ADR 0003 의 vocab-ext cycle 로 어휘 확장 → 자동화 가능 (이미 backfill 진행 중) |

## 5. ADR 0003 (vocabulary-extension) cycle 과의 연결

ADR `docs/adr/0003-vocabulary-extension-skill.md` + commit `201d48a` + backfill `9d715f1` 로 이미 설계된 메커니즘:

- 손-어댑터 = *임시* 폴백. case .md frontmatter `vocab_candidates` 에 패턴 축적
- 임계 도달 (`high≥1 + total≥3` 또는 `med≥3`) → `/vocabulary-extension` 손-호출 → 어휘 확장 평가·박기
- backfill (4/4 중 3건 완료, ArcaLive case .md 부재) 후 **첫 임계 도달**: `response_branch_body` = 3건 — vocab-ext 호출 권장 상태 (현재 dashboard `/vocab-deferred` 에 노출 중)

### 본 bench 가 cycle 에 더한 점

bench artifact = **새 vocab_candidate evidence source**. 코드 grep 이 아니라 *실제 도구 실행 결과* 가 evidence:

| 사이트 | bench 가 폭로한 패턴 | vocab candidate 후보 |
|---|---|---|
| nexon_bluearchive | HTML 0 글 + JSON API 같은 호스트 (`/api/v1/board/<id>/threads`) | `host_redirect_to_api` 또는 `inline_api_endpoint` |
| arca_trickcal | naive playwright 안 통과, `webdriver=undefined` + UA spoof 로 통과 | `fingerprint_hide_required` |
| naver_cafe | `g_sClubId` HTML → cafe API (이미 `html_chain_to_api` 등록됨) | (기존 vocab 강화 evidence) |

→ 다음 hand-config 진입 시 위 사이트 case .md 에 `vocab_candidates` 추가 가능. evidence path = `experiments/prior-art-bench/results/<tool>/<slug>__run<N>.json`.
